== AsyncFIFO — Introduction
* Write in one clock domain, read in another.
* Safe, high-throughput CDC for multi-bit data.
* Hard to get right: subtle bugs can be rare but costly.
* Use proven techniques (Gray pointers, 2-FF sync, full/empty rules).

[.notes]
--
Un FIFO asíncrono es un tipo de FIFO donde los datos se escriben en un dominio de reloj y se leen en otro, siendo ambos dominios de reloj asíncronos entre sí. Proporciona un mecanismo seguro para transferir datos entre dominios de reloj. El diseño correcto de FIFOs asíncronos no es trivial, ya que muchos diseños incorrectos parecen funcionar correctamente la mayoría del tiempo. Incluso los diseños que funcionan el 99% del tiempo pueden contener errores sutiles relacionados con CDC. Estos errores intermitentes suelen ser difíciles de reproducir y muy costosos de detectar o corregir una vez en producción. Por lo tanto, es crucial utilizar técnicas de diseño probadas al implementar FIFOs asíncronos.

https://www.deepchip.com/posts/0357.html

--

== Passing Multiple Asynchronous Signals
* Aligning several changing signals to one dst cycle is unreliable.
* Use a FIFO: write under WCLK, read under RCLK.
* Real challenge = pointers across domains + FULL/EMPTY detection.

[.notes]
--
La sincronización de múltiples señales cambiantes de un dominio de reloj a otro, asegurando que todas se alineen con el mismo ciclo de reloj de destino, es altamente problemática. Para transferir de manera segura palabras de datos de varios bits a través de dominios de reloj asíncronos, se utilizan FIFOs: las palabras de datos se escriben en una memoria búfer FIFO bajo el control del dominio de reloj de escritura y se leen desde la misma memoria búfer FIFO bajo el control del dominio de reloj de lectura.
--

== Asynchronous FIFO Pointers (I)
* Write pointer → next write location.
* Read pointer → current read location.
* After reset: both 0, FIFO empty; first write makes data immediately readable.

[.notes]
--
Para comprender el diseño de FIFOs asíncronos, es esencial entender cómo operan los punteros FIFO. El puntero de escritura siempre apunta a la siguiente ubicación que se escribirá, y el puntero de lectura siempre apunta a la ubicación actual que se leerá. Al reiniciar, ambos punteros se establecen en cero y el FIFO está vacío, con el puntero de lectura dirigiéndose a datos inválidos. En la primera escritura, el puntero de escritura se incrementa, se borra la bandera de vacío y el puntero de lectura ahora apunta a la primera palabra de datos válida, haciéndola inmediatamente disponible en el puerto de salida del FIFO. Este diseño asegura que el receptor pueda leer una palabra en un ciclo de reloj sin necesidad de un ciclo adicional para incrementar el puntero, mejorando la eficiencia.
--  

== Asynchronous FIFO Pointers (II)
* Empty: read_ptr == write_ptr (all bits equal).
* Full: same low bits, but MSB differs (extra wrap bit).
* Depth = 2^N → pointers = N+1 bits (N for addr + 1 for wrap).

[.notes]
--
El FIFO está vacío cuando ambos punteros (lectura y escritura) son iguales. Esto ocurre después del reinicio (ambos en cero) y cuando el puntero de lectura alcanza al puntero de escritura después de leer la última palabra. Sin embargo, el FIFO también está lleno cuando ambos punteros son iguales nuevamente, después de que el puntero de escritura da la vuelta y alcanza al puntero de lectura. Para distinguir entre lleno y vacío, cada puntero incluye un bit extra (MSB): cuando el puntero de escritura da la vuelta, su MSB cambia, lo mismo ocurre con el puntero de lectura. Por lo tanto, vacío significa que todos los bits del puntero (incluido el MSB) son iguales, mientras que lleno significa que todos los bits excepto el MSB son iguales y los MSBs difieren. El uso de punteros de n bits para un FIFO con 2^(n-1) ubicaciones de memoria proporciona un mecanismo limpio y confiable para detectar condiciones de lleno y vacío.
--

== Binary Pointers vs Gray (Why Gray?)
* Binary counters flip multiple bits → unsafe to sync.
* Handshake can work but adds latency/area.
* Gray code flips 1 bit per step → safer cross-domain sync.

[.notes]
--
Sincronizar un contador binario a través de dominios de reloj es problemático porque múltiples bits pueden cambiar simultáneamente. Para transferir de manera segura dichos valores entre relojes asíncronos, se puede utilizar una sincronización basada en handshake: el dominio de origen muestrea y mantiene el contador binario en un registro, luego afirma una señal de listo al dominio de destino. Al detectar la señal de listo, el destino envía de vuelta un reconocimiento. El dominio de origen luego borra el listo y vuelve a muestrear. Esto asegura que el valor binario muestreado permanezca estable hasta que se capture de manera segura en el nuevo dominio de reloj. Aunque el puntero sincronizado puede no coincidir exactamente con el valor más reciente, no ocurrirá desbordamiento ni subdesbordamiento. Sin embargo, debido a que los contadores binarios pueden cambiar múltiples bits por transición, un enfoque más robusto y eficiente es utilizar contadores de código Gray, donde solo un bit cambia por paso, minimizando la incertidumbre de sincronización.
--

== Gray Code Essentials
* 1-bit change between adjacent codes.
* FIFO depth should be a power of two (2^N).
* Keep binary pointer for RAM addr, Gray pointer only for synchronization.

[.notes]
--
Un código Gray tiene una distancia de código de 1 entre valores adyacentes, lo que significa que solo un bit cambia entre conteos sucesivos. Esta propiedad de transición de un solo bit hace que los códigos Gray sean ideales para punteros FIFO asíncronos, ya que evita problemas de metastabilidad que surgen cuando múltiples bits cambian simultáneamente. Las propiedades importantes de los contadores de código Gray incluyen que la secuencia de conteo debe tener una longitud que sea una potencia de 2 (por ejemplo, 2^n) y que las secuencias de código Gray con longitudes impares (por ejemplo, 23 estados) no son posibles. Aunque existen códigos Gray de longitud par que no son potencias de 2, son menos prácticos debido a la complejidad adicional en las conversiones a y desde binario. Por lo tanto, los FIFOs asíncronos basados en punteros codificados en Gray se diseñan con matrices de memoria de profundidad 2^n para alinearse con las propiedades naturales del conteo en código Gray.
--

== FIFO Design Lab (What you'll build)
* Dual-clock FIFO with:
** Binary+Gray write/read pointers.
** 2-FF synchronizers for cross-domain pointers.
** FULL/EMPTY generation.
** Simple dual-port RAM model.

[.notes]
--
El diseño del FIFO asíncrono se divide en seis módulos Verilog, cada uno con una funcionalidad específica y asociación de dominio de reloj. Estos incluyen un módulo envolvente de nivel superior, un búfer de memoria FIFO, sincronizadores de punteros de lectura a escritura y de escritura a lectura, y lógica para los punteros de lectura y escritura junto con las banderas EMPTY y FULL.

== Module Partitioning (Quick Map)
* `fifo1` — top wrapper & wiring.
* `fifomem` — dual-port RAM (wclk write, rclk read).
* `sync_r2w` — sync read Gray into write domain.
* `sync_w2r` — sync write Gray into read domain.
* `rptr_empty` — read ptr (bin+gray) + EMPTY.
* `wptr_full`  — write ptr (bin+gray) + FULL.

== MCP Handshaking vs Async FIFO

[cols="20,40,40",options="header,autowidth"]
|===
| Aspect | MCP (req/ack) | Async FIFO

| Throughput
| 1 word / round-trip
| ~1 word / dst clk

| Latency
| 2–4 cycles (src+dst)
| ~1 dst cycle after sync

| Bursts / drift
| Weak (single-word buffer)
| Strong (depth buffers)

| Area
| Tiny logic
| RAM + pointers + sync

| Best for
| Control / events / config
| Streams / DMA / packets
|===

[.notes]
--
Los FIFOs asíncronos y los mecanismos de handshake MCP (solicitud/reconocimiento) son dos enfoques diferentes para la transferencia de datos entre dominios de reloj asíncronos. Los FIFOs asíncronos son ideales para flujos de datos continuos y de alto rendimiento, como transmisiones de video o audio, donde se requiere un alto ancho de banda y la capacidad de manejar ráfagas de datos. Por otro lado, los mecanismos MCP son más adecuados para transferencias de datos esporádicas o de baja velocidad, como señales de control o eventos, donde la latencia no es tan crítica y el volumen de datos es bajo. En resumen, los FIFOs asíncronos son preferibles para flujos de datos intensivos, mientras que los MCP son más adecuados para comunicaciones de control y eventos.
--
