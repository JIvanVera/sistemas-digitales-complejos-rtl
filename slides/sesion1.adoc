== Reset Design — Motivation and Background

=== Reset Design — Motivation and Background
[.text-justify]
**Reset design** is a surprisingly complex topic that is often **poorly emphasized** in engineering education.

[.text-justify]
- Improper reset strategies can lead to **real design failures**.
- Industry experience shows that reset handling is often **underestimated**.

[.notes]
--
El reset parece algo sencillo, pero en la práctica es complejo.
El diseño del reset es un tema complejo y a menudo poco enfatizado en la educación.
Errores en el reset pueden causar fallos reales en el diseño.
La experiencia en la industria muestra que a menudo se subestima su importancia.
--

=== Synchronous vs. Asynchronous Resets

[.text-justify]
The choice between **synchronous** and **asynchronous** resets has become almost a *religious debate*  
in the hardware design community.

[.text-justify]
- Both approaches are valid — each with **strengths and weaknesses**
- The key is to understand **when and how** to apply each method properly.

[.notes]
--
La elección entre resets síncronos y asíncronos es un tema que genera mucho debate.
Ambos enfoques son válidos, cada uno con sus ventajas y desventajas.
Lo importante es entender cuándo y cómo aplicar cada método correctamente.
--

=== Why Resets Matter

[.text-justify]
**Why care about these annoying little resets?**  
Because they bring a system back to a **known working state** — and that can be the difference between recovery and failure.

[.text-justify]
- A **hardware reset** initializes every chip in a system to a stable condition.
- Even in PCs, the **reset button** is often the most reliable “fix” when things go wrong.
- In ASICs, resets ensure that simulation, synthesis, and silicon all **start from a predictable state**.

[.text-justify]
A well-designed reset system ensures **functional correctness, reproducibility, and testability**.

[.notes]
--
¿Por qué preocuparnos por los resets? Porque permiten volver a un estado conocido, lo que puede ser la diferencia entre recuperación y fallo.
Un buen sistema de reset asegura corrección funcional, reproducibilidad y testabilidad.
--

=== The Purpose of Reset in ASICs

[.text-justify]
For ASICs, the reset has one primary goal:  
**force the design into a known state** for simulation and reliable startup.

[.text-justify]
- Some ASICs (e.g., data-path or communication designs) can **self-synchronize** without resets.
- However, most designs require at least a **power-up reset** to ensure all logic starts correctly.
- Even unused states in FSMs should point to a **safe initialization path**.

[.text-justify]
In general:

- Every flip-flop **should be resettable**, even if not always used by the system.
- High-speed pipelines may **omit resets** to meet timing.
- Designers must plan **reset trees**, buffering, and verification with care.

[.notes]
--
No todos los chips necesitan un reset externo para funcionar, pero casi todos lo agradecen para arrancar de forma determinista.
En datapaths, si las FSMs están bien diseñadas, pueden re-sincronizarse; aún así, el resto del sistema debe quedar en estado seguro.
Como regla, reseteamos todo; excepción: followers de pipelines críticos para frecuencia.
Además del estilo, hay que diseñar el árbol de distribución, verificar recovery/removal, contemplar DFT y pensar en dominios de reloj múltiples.
--

== General Flip-Flop Coding Styles

=== Bad Flip-Flop Coding Style (Part I)
[.text-justify]
Each Verilog procedural block should **model only one type of flip-flop**.  
Mixing **resettable** and **non-resettable** (follower) flops in the same block leads to **unwanted logic**.

[.text-justify]
- A *follower flip-flop* is a simple data shift register with no reset.
- When both are coded together, the reset signal may be **interpreted as a data enable** for the follower stage.
- This results in **extra combinational logic**, as it is shown.

=== Bad Flip-Flop Coding Style (Part II)

[cols="50a,50a"]
|===
| 
[source,verilog]
----
module badFFstyle (
  input  logic clk, 
  input  logic rst_n, 
  input  logic d,
  output logic q2
);
  logic q1;
  always_ff @(posedge clk)
    if (!rst_n)
      q1 <= 1'b0;
    else begin
      q1 <= d;
      q2 <= q1;
    end
endmodule
----
| 
image::bad_ff_style.svg[width=90%]
|===

[.small-text]
Bad Verilog coding style: mixing resettable and follower flip-flops.

https://www.intel.com/content/www/us/en/docs/programmable/683539/20-4/coding-synchronous-reset-with-follower.html

=== Correct Flip-Flop Coding Style

[.text-justify]
To avoid unintended logic, model **each flip-flop type** in its **own procedural block**.

[.text-justify]
- Separate resettable and non-resettable flops.
- This style produces **clean synthesis results**, as it is shown below.
- If asynchronous resets were used, both coding styles would synthesize identically.

[cols="50a,50a"]
|===
| 
[source,verilog]
----
module goodFFstyle (
  input  logic clk, 
  input  logic rst_n, 
  input  logic d,
  output logic q2
);
  logic q1;

  // Resettable flip-flop
  always_ff @(posedge clk)
    if (!rst_n)
      q1 <= 1'b0;
    else
      q1 <= d;

  // Follower flip-flop
  always_ff @(posedge clk)
    q2 <= q1;
endmodule
----
|

|===

=== Flip-Flop Inference Style

[.text-justify]
When modeling flip-flops in RTL, **inference style** is key for readability and synthesis efficiency.

[.text-justify]
- All **inferred flip-flops of a common function** (or group of related functions)  
  should be described in **a single procedural block** (`always` or `process`).
- Use **multiple blocks** only for **larger partitioned functional groups**.

[.text-justify]
This ensures:

- Consistent **reset behavior** and **timing grouping**
- Simplified **simulation and synthesis**
- Cleaner and more **maintainable RTL**

https://github.com/lowRISC/ibex/blob/master/rtl/ibex_if_stage.sv#L498


[.notes]
--
El estilo de inferencia es clave para la legibilidad y eficiencia de síntesis.
Agrupad flops relacionados en un mismo bloque `always_ff` para mantener consistencia en reset y timing.
Usad múltiples bloques sólo para grupos funcionales grandes y separados.
Esto facilita la simulación, síntesis y mantenimiento del RTL.
--

== ⏱ Synchronous Resets

=== Concept

[.text-justify]
A **synchronous reset** affects a flip-flop’s state **only on the active clock edge**.  
It can be modeled as part of the **combinational logic** driving the `d` input.

[.text-justify]
Recommended coding style:
[source,verilog]
----
always @(posedge clk)
  if (reset)
    q <= 1'b0;
  else
    q <= d;
----

[.text-justify]
⚠️ **Two common pitfalls:**

- **Simulation issue:**  
  If reset is not given top priority (`if` branch), logic may block it in simulation.
- **Late reset arrival:**  
  Reset may reach flip-flops too late due to **high fanout** and buffering delays.

[.text-justify]
Limiting reset logic depth and fanout improves **timing reliability**.

[.notes]
-- 
El reset síncrono actúa sólo en el flanco de reloj activo y se modela como parte de la lógica combinacional que alimenta `d`.
Usad `if (reset)` en el `always_ff @(posedge clk)` para darle máxima prioridad.
Cuidado con dos problemas comunes: en sim, si no es prioridad, puede bloquearse; en síntesis, el reset puede llegar tarde por fanout alto.
Limitad la profundidad y fanout del reset para mejorar la fiabilidad temporal.
--

=== Example: Loadable counter with synchronous reset

[cols="50a,50a"]
|===
| 
[source,systemverilog]
----
module ctr8sr (
  input  logic        clk,
  input  logic        rst_n,  // active low reset
  input  logic        load,
  input  logic [7:0]  d,
  output logic [7:0]  q,
  output logic        co
);
  always_ff @(posedge clk) begin
    if (!rst_n)         // sync reset
      {co,q} <= '0;
    else if (load)      // sync load
      {co,q} <= d;
    else                // sync increment
      {co,q} <= q + 1'b1;
  end
endmodule
----

=== Preventing Synchronous Reset Issues in Synthesis

[.text-justify]
Synopsys provides the directive:
[.highlight]
`// synopsys sync_set_reset "rst_n"`

[.text-justify]
This tells the tool that **`rst_n` is a synchronous reset**, forcing the reset signal  
to be **pulled as close to the flip-flop as possible** — ensuring proper initialization.

[.text-justify]
✅ **Recommendations:**

- Use `sync_set_reset` once per module that includes synchronous resets.  
- Alternatively, set the global synthesis variable:
  [source]
  ----
  set hdlin_ff_always_sync_set_reset true
  ----
- Avoid older variables like:
  `compile_preserve_sync_resets = "true"` (deprecated since Synopsys v3.4b)

[.text-justify]
Including this directive early prevents **re-synthesis late in the project**  
and avoids **simulation mismatches** between RTL and gate-level models.

[.notes]
--
Synopsys ofrece la directiva `// synopsys sync_set_reset "rst_n"` para indicar que `rst_n` es un reset síncrono.
Esto fuerza a la herramienta a colocar el reset lo más cerca posible del flip-flop, asegurando una inicialización correcta.
Recomendaciones: usad `sync_set_reset` una vez por módulo con resets síncronos, o estableced la variable global `hdlin_ff_always_sync_set_reset true`.
Evitad variables obsoletas como `compile_preserve_sync_resets = "true"`.
Incluir esta directiva desde el principio previene re-síntesis tardía y evita discrepancias de simulación entre RTL y gate-level.

=== Advantages of Synchronous Resets (Part I)

[.text-justify]
Synchronous resets are widely used because they keep the design **fully synchronous**  
and simplify **timing analysis** and **verification**.

[.text-justify]
**Technical advantages:**

- May **reduce flip-flop area** (smaller cells if reset is merged with D-input logic)  
  — though total gate savings are often minor.
- Reset occurs **only on clock edges**, ensuring predictable timing.
- The clock acts as a **glitch filter** for the reset signal.
- Suitable when resets are **generated internally**, filtering logic equation glitches.
- Can use **pipeline stages within the reset buffer tree** to meet clock timing.

[.notes]
--
Los resets síncronos mantienen el diseño totalmente síncrono y simplifican análisis y verificación.
Ventajas técnicas: posible reducción de área en FFs, timing predecible, filtrado de glitches, adecuados para resets internos y permiten pipelining en el árbol de reset.
--

=== Advantages of Synchronous Resets (Part II)

[.text-justify]
**Practical considerations:**

- Recommended by the *Reuse Methodology Manual (RMM)*  for ease of use with **cycle-based simulators**.
- In modern ASICs, **area savings are negligible**.
- With proper testbench design, **simulation speed differences are minimal**.

[.small-text]
Summary: Synchronous resets improve determinism and timing control,  
but provide little benefit in area or simulation performance.

[.notes]
--
Los resets síncronos son recomendados por el RMM para facilitar el uso con simuladores basados en ciclos.
En ASICs modernos, el ahorro de área es insignificante y con un buen testbench la diferencia de velocidad en sim es mínima.
--  


=== Disadvantages of Synchronous Resets (Part I)

[.text-justify]
While synchronous resets simplify timing, they also introduce **practical limitations**  
that can complicate simulation, multi-clock design, or low-power operation.

[.text-justify]
**Technical issues:**

- Not all ASIC libraries include flip-flops with **built-in synchronous resets**.  
  Reset must often be synthesized as extra logic before the flop.

- May require a **pulse stretcher** to guarantee the reset is active  
  for at least one **clock edge** — important in multi-clock systems.

- **X-masking in simulation:**  
  Reset signals generated through combinational logic can be blocked by *unknown (X)* values.  
  This has been a recurring topic in **ESNUG** and **SNUG** discussions.

[.notes]
--
Aunque los resets síncronos simplifican el timing, también introducen limitaciones prácticas que pueden complicar la simulación, el diseño multi-reloj o la operación de bajo consumo.
Problemas técnicos: no todas las librerías ASIC tienen FFs con reset síncrono integrado; puede necesitarse un estirador de pulso para garantizar activación en un flanco; en sim, el reset puede ser bloqueado por valores X en la lógica combinacional.
--

=== Disadvantages of Synchronous Resets (Part II)

[.text-justify]
**Functional limitations:**

- A clock is **required to perform a reset**.  
  If the clock is **gated off** for power saving, reset cannot propagate.

- During **power-up**, synchronous resets cannot initialize tri-state buses  
  unless additional logic de-asserts the enable path.

[.text-justify]
**Design implications:**

- Works well for synchronous systems, but less ideal for  
  **power-gated**, **multi-clock**, or **mixed-reset** architectures.

[.notes]
--
Se requiere un reloj para realizar un reset. Si el reloj está apagado para ahorrar energía, el reset no puede propagarse. 
Durante el power-up, los resets síncronos no pueden inicializar buses triestado sin lógica adicional.
Diseño: funciona bien en sistemas síncronos, pero es menos ideal para arquitecturas con power-gating, multi-reloj o resets mixtos.
--

== ⏱ Asynchronous Resets
=== Asynchronous Resets — Introduction

[.text-justify]
Asynchronous resets are widely used because they allow logic to **immediately enter a known state**,  
independent of the clock.

[.text-justify]
However, improper implementation can cause **severe functional failures** in digital systems.

[.text-justify]
- Reset is applied and recognized **without waiting for a clock edge**.  
- Commonly implemented using **flip-flops with a dedicated reset pin**, usually active-low.  
  When `reset_n` = 0 → the flip-flop is forced to its reset state.

[.warning]
**Main challenge:**  
The *reset release* (also called *reset removal*) — if not handled correctly,  
can lead to **metastability**, **glitches**, or **unpredictable startup behavior**.

[.notes]
--
Los resets asíncronos permiten que la lógica entre inmediatamente en un estado conocido, independiente del reloj.
Sin embargo, una implementación incorrecta puede causar fallos funcionales graves.
El principal desafío es la liberación del reset: si no se maneja correctamente, puede llevar a metastabilidad, glitches o comportamientos impredecibles al arrancar.
--


=== Asynchronous Resets — Correct Coding Style (Part I)

[.text-justify]
In Verilog and VHDL, the **asynchronous nature** of a reset is defined  
by including the reset signal in the **sensitivity list**.

[.text-justify]
**Verilog example:**
[source,verilog]
----
always @(posedge clk or negedge rst_n)
  if (!rst_n)
    q <= 1'b0;
  else
    q <= d;
----

[.notes]
--
En Verilog y VHDL, la naturaleza asíncrona de un reset se define incluyendo la señal de reset en la lista de sensibilidad.
--

=== Asynchronous Resets — Correct Coding Style  (Part II)

[.text-justify]
**Key synthesis and simulation notes:**

- In Synopsys, if any signal in the sensitivity list is edge-sensitive,  
  **all must be edge-sensitive** → enforces correct coding style.
- Only **clock** and **reset** signals should appear in the sensitivity list.  
  Adding others causes **simulation mismatches** and **synthesis errors**.

[.small-text]
Good style → predictable simulation, valid synthesis, and cleaner reset timing.

[.notes]
--
Notas clave de síntesis y simulación: en Synopsys, si alguna señal en la lista de sensibilidad es sensible a flancos, todas deben serlo; esto refuerza el estilo de codificación correcto. Solo el reloj y las señales de reset deben aparecer en la lista de sensibilidad; agregar otras causa discrepancias de simulación y errores de síntesis.
--

=== Async Reset in Synthesis (Synopsys DC)

[.text-center]
Reset nets must be **protected** from optimization.

* If reset comes from an **external pin**:
  - `set_drive 0 [get_ports reset]`
  - `set_dont_touch_network [get_nets reset]`

[.text-center]
* To clean timing reports:
  - `set_disable_timing [get_nets reset]`
  - `set_false_path -from [get_ports reset]`

[.text-center]
⚠️ Goal: Ensure reset nets are **not modified** and do not introduce false timing violations

[.notes]
--
Proteger la red de reset para que el sintetizador no la “optimice”.  
Además, limpiad informes con `false_path` o `disable_timing` donde tenga sentido, evitando falsos positivos.
--

=== Advantages of Asynchronous Resets (Part I)

[.text-justify]
Asynchronous resets provide a **clean and direct way** to initialize logic,  
without impacting the data path timing.

[.text-justify]
**Technical advantages:**

- Reset logic is handled **outside the data path** → no additional delay or logic on `D` input.  
  Ideal for **high-performance designs** with tight timing margins.
- Guaranteed that **reset logic** will not be added to the combinational data network.
- Circuit can be reset **independently of the clock**,  
  allowing initialization even when the clock is gated or stopped.

[.notes]
--
Los resets asíncronos ofrecen una forma directa de inicializar la lógica sin afectar el timing del datapath.
Ventajas técnicas: el reset se maneja fuera del datapath, sin añadir retardo o lógica en `D`; ideal para diseños de alto rendimiento. Permite resetear independientemente del reloj, útil si el reloj está apagado.
--

=== Advantages of Asynchronous Resets (Part II)

[.text-justify]
**Practical benefits:**

- If the vendor library supports **flip-flops with asynchronous reset pins**,  
  synthesis tools will automatically map to the correct cells.
- Typically **no need for synthesis attributes** or manual mapping.
- Clean behavior during both **power-up** and **manual resets**.

[.small-text]
Summary: asynchronous resets isolate reset from data timing paths  
and provide flexibility for clock-independent initialization.

[.notes]
--
Beneficios prácticos: si la librería soporta FFs con pines de reset asíncrono, las herramientas de síntesis mapearán automáticamente a las celdas correctas, sin necesidad de atributos o mapeos manuales. Comportamiento limpio durante power-up y resets manuales.
--

=== Disadvantages of Asynchronous Resets (Part I)

[.text-justify]
Although widely used, asynchronous resets can introduce **simulation, test, and timing challenges**  
if not handled carefully.

[.text-justify]
**Practical limitations:**

- For **DFT (Design for Test)**, if the asynchronous reset is **not driven from an I/O pin**,  
  it must be **disabled** during scan operations.
- **Static timing analysis (STA)** is more complex — reset release must meet  
  a **one-clock-period constraint** across the entire reset tree.
- Proper timing validation requires **post-layout analysis**.

[.notes]
--
Aunque son ampliamente usados, los resets asíncronos pueden introducir desafíos de simulación, prueba y timing si no se manejan con cuidado.
Limitaciones prácticas: para DFT, si el reset asíncrono no viene de un pin I/O, debe deshabilitarse en scan; el análisis estático de timing es más complejo, ya que la liberación del reset debe cumplir una restricción de un ciclo en todo el árbol; se requiere análisis post-layout.
--

=== Disadvantages of Asynchronous Resets (Part II)

[.text-justify]
**Critical risks:**

- The **de-assertion** of reset (reset removal) near a clock edge can cause **metastability**,  
  corrupting the known reset state.
- Sensitive to **noise or glitches** on system reset lines → may cause **spurious resets**.
- Even synchronous resets can fail if spurious pulses occur near clock edges.

[.small-text]
Summary: asynchronous resets require careful release timing and reset tree analysis  
to avoid metastability and unpredictable startup behavior.

[.notes]
--
Riesgos críticos: la desactivación del reset cerca de un flanco de reloj puede causar metastabilidad, corrompiendo el estado conocido; son sensibles a ruido o glitches en las líneas de reset, lo que puede causar resets espurios. Incluso los resets síncronos pueden fallar si ocurren pulsos espurios cerca de los flancos de reloj.
--

=== The Asynchronous Reset Problem (Part I)

[.text-justify]
Many engineers believe that FPGAs and ASICs behave differently regarding resets —  
**they do not**. The same **asynchronous reset issues** apply to both.

[.text-justify]
**Common misconception:**

> “An asynchronous system reset can always safely bring the chip to a known state.”

[.notes]
-- 
Muchos ingenieros creen que FPGAs y ASICs se comportan de manera diferente con respecto a los resets; no es así. Los mismos problemas de resets asíncronos se aplican a ambos.
--

=== The Asynchronous Reset Problem (Part II)

[.text-justify]
In reality:

- If **reset is released** (*de-asserted*) **near a clock edge**,  
  flip-flops may enter a **metastable state**.
- Designs may pass all **simulations**, yet fail **intermittently in hardware**.
- Reset removal must be handled carefully to prevent **unknown system states**.

[.notes]
-- 
En realidad, si el reset se libera cerca de un flanco de reloj, los flip-flops pueden entrar en un estado metastable. Los diseños pueden pasar todas las simulaciones, pero fallar intermitentemente en hardware. La liberación del reset debe manejarse con cuidado para prevenir estados desconocidos del sistema.
--

=== Reset Recovery & Removal Timing

[.text-justify]
Improper timing of reset release can lead to **metastability** or **inconsistent initialization**.

[.float-group]
--
image::rem_rec_reset.svg[width=40%]
--

=== Reset recovery time
- Refers to the time between **reset de-assertion** and the next **active clock edge**.
- Modeled in Verilog-2001 using:
  `$recovery`, `$removal`, and `$recrem` (*combined check*).
- Equivalent to a **setup time**:  
  *“PRE or CLR inactive setup time before CLK↑”*.
- Violating recovery time may cause **metastable or undefined outputs**.

[.notes]
--
El tiempo de recuperación del reset se refiere al tiempo entre la desactivación del reset y el siguiente flanco de reloj activo. Se modela en Verilog-2001 utilizando: $recovery, $removal y $recrem (verificación combinada).
--

=== Reset removal time
- When reset removal is **asynchronous**, propagation delays may cause  
  some flip-flops to **exit reset earlier than others**.
- The result: **different parts of the circuit** begin operation in **different cycles**.
- Leads to **intermittent startup errors** or **partial initialization**.

[.small-text]
Summary: ensure that reset release timing respects $recovery / $removal checks  
and that all flip-flops exit reset synchronously.

[.notes]
--
El tiempo de eliminación del reset, cuando es asíncrono, puede causar que algunos flip-flops salgan del reset antes que otros debido a retrasos de propagación. Esto puede llevar a errores intermitentes al arrancar o inicialización parcial.
--

=== Reset Synchronizer

[.highlight]
EVERY ASIC USING AN ASYNCHRONOUS RESET SHOULD INCLUDE A
RESET SYNCHRONIZER CIRCUIT!!

=== Reset Synchronizer

[.text-justify]
Without a reset synchronizer, an **asynchronous reset** may fail in real hardware  
even if it appears to work perfectly during simulation.

[.text-justify]
The reset synchronizer combines the **advantages** of both asynchronous and synchronous resets:

- An **external asynchronous reset** drives a pair of *master reset flip-flops*.
- These flip-flops propagate the reset signal **asynchronously** to the entire design  
  through the **reset buffer tree** → all flip-flops are reset immediately.
- **Reset removal** occurs synchronously:  
  the first flip-flop’s D-input is tied to `1'b1` and is clocked through the synchronizer.
- Typically, it takes **two clock cycles** after reset release for the reset to be safely removed.

[.notes]
--
Sin un sincronizador de reset, un reset asíncrono puede fallar en hardware real incluso si parece funcionar perfectamente durante la simulación.
El sincronizador de reset combina las ventajas de ambos tipos de resets: un reset asíncrono externo impulsa un par de flip-flops maestros de reset. Estos flip-flops propagan la señal de reset asíncronamente a todo el diseño a través del árbol de buffers de reset, reseteando todos los flip-flops inmediatamente. La liberación del reset ocurre síncronamente: la entrada D del primer flip-flop está atada a `1'b1` y se clockea a través del sincronizador. Normalmente, se necesitan dos ciclos de reloj después de la liberación del reset para que el reset se elimine de manera segura.
--

=== Reset Synchronizer Metastability??

[.text-justify]
Could the **reset synchronizer** go itself into **metastable** when reset is released?

[.text-justify]
👉 The answer: **NO**

- The **first flip-flop** *can* go metastable  
  if reset is removed too close to the rising clock edge  
  → this is within the **reset recovery window**.
- The **second flip-flop** is immune:  
  when reset is released, both its input and output are **logic 0**,  
  so there’s **no differential** to cause oscillation or instability.

[.notes]
--
¿Puede el sincronizador de reset volverse metastable? La respuesta es NO. El primer flip-flop puede volverse metastable si el reset se elimina demasiado cerca del flanco ascendente del reloj, dentro de la ventana de recuperación del reset. El segundo flip-flop es inmune: cuando se libera el reset, tanto su entrada como su salida son lógicas 0, por lo que no hay diferencial que cause oscilación o inestabilidad.
--

== Simulation Testing with Resets

=== Simulation Testing with Resets
[.text-justify]
In simulation, if **reset** is de-asserted on a **posedge clock**, results are *not guaranteed*:

- **RTL and gate-level** simulations may behave **differently**  due to event scheduling race conditions.
- Different **IEEE-Verilog compliant simulators** may even yield **different results**.
- ASIC library models often drive **`X` outputs** on reset recovery time violations  
  (typically modeled via a **UDP – User Defined Primitive**).

[.notes]
--
En simulación, si el reset se desactiva en un flanco positivo del reloj, los resultados no están garantizados: las simulaciones RTL y gate-level pueden comportarse de manera diferente debido a condiciones de carrera en la programación de eventos. Diferentes simuladores compatibles con IEEE-Verilog pueden incluso producir resultados diferentes. Los modelos de librerías ASIC a menudo generan salidas `X` en violaciones del tiempo de recuperación del reset (normalmente modeladas mediante un UDP - User Defined Primitive).
--  

=== ✅ Recommended Guidelines
- Always **change the reset** on the **inactive clock edge**,  
  far from any potential **recovery time violation**.
- Use **blocking assignments** for reset transitions in the testbench.
- Assert **reset at time 0** to initialize all registers and flip-flops.
- Use a **nonblocking assignment (`<=`)** at time 0 to avoid Verilog race conditions.

[.notes]
--
Siempre cambiad el reset en el flanco inactivo del reloj, lejos de cualquier posible violación del tiempo de recuperación. Usad asignaciones bloqueantes para las transiciones de reset en el testbench. Afirmad el reset en el tiempo 0 para inicializar todos los registros y flip-flops. Usad una asignación no bloqueante (`<=`) en el tiempo 0 para evitar condiciones de carrera en Verilog.
--

=== Example — Good Testbench Reset Handling
[source,verilog]
----
initial begin // clock oscillator
  clk <= 0;               // time 0 nonblocking assignment
  forever #(`CYCLE/2) clk = ~clk;
end

initial begin
  rst_n <= 0;             // time 0 nonblocking assignment
  @(posedge clk);         // wait past time 0
  @(negedge clk) rst_n = 1; // rst_n low for one cycle
  ...
end
----

[.small-text]
Figure: Safe reset stimulus avoids race conditions and ensures  
consistent results in both RTL and gate-level simulations.

[.notes]
--
Ejemplo de manejo seguro del reset en el testbench para evitar condiciones de carrera y asegurar resultados
consistentes en simulaciones RTL y gate-level.
--

=== Overview

[.text-center]
* The **reset distribution tree** needs almost as much care as the **clock tree**
* Typically, there are as many reset loads as clock loads
* Key difference:
  - Clock skew must be tightly controlled
  - Reset skew is less critical — but **must still meet recovery time**

* Design tip:
  - Always analyze **clock vs. reset timing**
  - Reset should not violate setup/hold on flip-flops

* Ignoring reset tree design can lead to **unpredictable behavior**

[.notes]
--
El árbol de reset no exige skew tan ajustado como el de reloj, pero sí llegar a tiempo para cumplir recovery.  
Comparad rutas de reloj y reset y evitad violaciones de setup/hold en destinos.
--


=== Synchronous Reset Distribution Technique (Part I)

[.text-justify]
For **synchronous resets**, a practical technique is to build a **distributed reset tree**  
with **flip-flops embedded** at each module level.

[.text-justify]
Key Idea:

- Each module registers its incoming reset signal:
  - The registered version drives internal logic.
  - It also drives the reset input of any submodules.
- Thus, it may take **several clock cycles**  
  for all flip-flops in the design to be reset.

[.notes]
--
Para resets síncronos, una técnica práctica es construir un árbol de reset distribuido con flip-flops embebidos en cada nivel de módulo.
Cada módulo registra su señal de reset entrante: la versión registrada impulsa la lógica interna y también impulsa la entrada de reset de cualquier submódulo.
Así, puede tomar varios ciclos de reloj para que todos los flip-flops en el diseño sean reseteados.
--

=== Synchronous Reset Distribution Technique (Part I)

[source,verilog]
----
input reset_raw;
// synopsys sync_set_reset "reset"
always @(posedge clk)
  reset <= reset_raw;   // synchronized local reset
----

=== Synchronous Reset Distribution Technique (Part II)

[.text-justify]
Advantages:

- Simplifies **timing analysis** → reset behaves like a local data signal.
- Reduces **fanout** and **tree delay** at each hierarchy level.
- Works well in **modular** and **multi-clock** designs.
- Provides predictable, stepwise reset release across modules.

[.note-box]
With this approach, reset propagates cleanly across hierarchy levels,  
but designers must account for the **multi-cycle delay** before the system is fully reset.

[.notes]
--
Ventajas: simplifica el análisis de timing, reduce fanout y delay del árbol en cada nivel jerárquico, funciona bien en diseños modulares y multi-reloj, y proporciona una liberación de reset predecible y escalonada a través de los módulos.
Con este enfoque, el reset se propaga limpiamente a través de los niveles jerárquicos, pero los diseñadores deben tener en cuenta el retraso de múltiples ciclos antes de que el sistema esté completamente reseteado.
--

=== Asynchronous Reset Distribution Technique

[.text-justify]
For **asynchronous resets**, a robust approach is to use a **distributed reset synchronizer tree**,  
similar to the synchronous reset tree, but with **two flip-flops per level** instead of one.

[.notes]
--
Para resets asíncronos, un enfoque robusto es usar un árbol de sincronizadores de reset distribuido, similar al árbol de reset síncrono, pero con dos flip-flops por nivel en lugar de uno.
--


=== Key Idea
- Each module contains a **local reset synchronizer**:
  - Two flip-flops ensure asynchronous **assertion** and synchronous **release**.
  - The local reset drives **asynchronous reset pins** of internal flip-flops.
- The reset propagates hierarchically —  
  it may take **several clock cycles** for the entire design to come out of reset.

[.notes]
--
Cada módulo contiene un sincronizador de reset local: dos flip-flops aseguran la afirmación asíncrona y la liberación síncrona. El reset local impulsa los pines de reset asíncrono de los flip-flops internos. El reset se propaga jerárquicamente, pudiendo tomar varios ciclos de reloj para que todo el diseño salga del reset.
--

=== Advantages
- Reset buffering and timing are **localized** per hierarchy level.
- **Synthesis tools** can automatically handle timing and buffering —  
  no manual P&R adjustments needed.
- Ideal for **FPGAs**, where:
  - GSR (Global Set/Reset) may cause unwanted async release issues.
  - Multiple clock domains can each have their own **local synchronizer**.
  - Saves **LUT resources** compared to synchronous resets.
- **DFT concerns** are irrelevant in FPGAs (no internal scan chains).

[.note-box]
This distributed reset-synchronizer method removes the need  
for complex backend reset-tree balancing while ensuring safe, deterministic reset release.

[.notes]
--
El árbol distribuido con sincronizadores locales por módulo es ideal para resets asíncronos.  
Cada módulo tiene su propio sincronizador de 2 FFs, que maneja afirmación asíncrona y liberación síncrona.
Esto localiza el buffering y timing, facilitando la síntesis y evitando ajustes manuales en P&R.
Perfecto para FPGAs, donde GSR puede causar problemas y cada dominio de reloj puede tener su propio sincronizador, ahorrando LUTs.
--

== Reset-Glitch
=== Reset-Glitch Filtering

[.text-justify]
If the **reset line is subject to glitches**,  
**any short pulse** that meets the minimum reset width  
can **unexpectedly reset** flip-flops — a **serious reliability issue**.

=== Problem
- Asynchronous resets react to **any valid pulse**, even spurious ones.  
- Glitches on the reset line → **undesired resets** or **system instability**.  

=== Solution
* Use a **digital delay–based glitch filter** to ignore narrow pulses.
* Input pad should be **Schmitt-triggered** for extra noise immunity.
* Delay can be implemented with:
  - Vendor **delay macros** or
  - A **chain of slow buffers** (ensure synthesis doesn’t optimize them away).

[.note-box]
Designers must evaluate whether their system reset source  
**requires glitch filtering** — not all systems do,  
but ignoring it can lead to **intermittent and hard-to-debug resets**.

[.notes]
--
Si la línea de reset está sujeta a glitches, cualquier pulso corto que cumpla el ancho mínimo puede resetear inesperadamente los flip-flops, causando problemas de fiabilidad.
Solución: usar un filtro de glitches basado en retardo digital para ignorar pulsos estrechos. La entrada debe ser Schmitt-triggered para mayor inmunidad al ruido. El retardo puede implementarse con macros de retardo del proveedor o una cadena de buffers lentos (asegurando que la síntesis no los optimice).
Evaluad si la fuente de reset requiere filtrado de glitches; ignorarlo puede llevar a resets intermitentes y difíciles de depurar.
--

== DFT
=== DFT for Asynchronous Resets

[.text-justify]
**Design-for-Test (DFT)** can be challenging with **asynchronous resets**,  
but only if the reset is part of the **functional logic**.  
When used **purely for initialization**, DFT remains simple and effective.

[.notes]
--
NO HABLAR DE DFT, DEJAR SOLO SLIDE PARA REFERENCUIA.
El DFT con resets asíncronos es sencillo si el reset se usa sólo para inicialización y no forma parte de la lógica funcional.
--

=== Key Guidelines
- Keep **asynchronous resets** outside functional data paths.  
  → Only reset synchronizers should contain reset logic.
- During **scan testing (ATPG)**:
  - The **reset signal must be held inactive** (non-reset state).  
  - If internally generated, mask it using a **test mode pin**.
- The **two flip-flops** of each reset synchronizer  
  should **not be included in the scan chain**.

[.notes]
--
Mantened los resets asíncronos fuera de los datapaths funcionales; sólo los sincronizadores deben contener lógica de reset.
Durante las pruebas de scan, el reset debe mantenerse inactivo; si es interno, enmasárcalo con un pin de modo test.
Los dos FFs de cada sincronizador no deben incluirse en la cadena de scan.  
--

=== Manual Reset Test Sequence
1. Scan in all `1`s into the scan chain.  
2. Assert and release reset.  
3. Scan out the result, then scan in all `0`s.  
4. Assert and release reset again.  
5. Scan out the result.  
6. Hold reset inactive and proceed with ATPG vectors.


== Multi-Clock Reset Issues

=== Multi-Clock Reset Issues (Part I)

[.text-justify]
In **multi-clock designs**, each clock domain must have its own  
**asynchronous reset synchronizer** and **reset distribution tree**.

==== Key Problem
- **Asserting** reset asynchronously is simple.  
- The challenge is the **safe release** of reset across different clock domains:
  - Prevent **recovery time violations**.
  - Ensure **synchronized startup** of logic.

[.notes]
--
En diseños multi-reloj, cada dominio debe tener su propio sincronizador y árbol de distribución de reset asíncrono.
El problema clave es la liberación segura del reset en diferentes dominios: evitar violaciones de recovery y asegurar un arranque sincronizado.
--

=== Multi-Clock Reset Issues (Part II)

==== Design Techniques
1. **Non-coordinated reset removal**  
   - Each clock domain releases reset independently.  
   - Simple implementation, may cause temporary inter-domain mismatches.

2. **Sequenced (coordinated) reset removal**  
   - Resets are de-asserted in a defined order.  
   - Ensures predictable system bring-up across all domains.

[.notes]
--
Técnicas de diseño para la liberación de resets en sistemas multi-reloj: eliminación no coordinada (cada dominio libera reset independientemente) y eliminación secuenciada (resets desactivados en un orden definido).
--  

=== Non-Coordinated Reset Removal (Part I)

[.text-justify]
In many **multi-clock systems**, the **relative timing** of reset release  
between clock domains **does not matter**.

==== Typical Scenario
- Each clock domain has its **own reset synchronizer**.  
- Resets (`arst_n`, `brst_n`, `crst_n`, …) may be released  
  **in any order or at different times**.  
- Cross-domain communication uses **handshake protocols**  
  (request/acknowledge), ensuring safe synchronization  
  even if domains start up at different times.

[.notes]
--
En muchos sistemas multi-reloj, el timing relativo de la liberación del reset entre dominios no importa.
Cada dominio tiene su propio sincronizador de reset. Los resets pueden liberarse en cualquier orden o en diferentes momentos. La comunicación entre dominios utiliza protocolos de handshake, asegurando una sincronización segura incluso si los dominios arrancan en diferentes momentos.
--

=== Non-Coordinated Reset Removal (Part II)

==== Design Implications
- Simple and robust — no coordination circuitry needed.  
- Works well when **cross-domain interactions** are protected  
  by **synchronizers or handshake logic**.

[.notes]
--
Sencillo y robusto, sin necesidad de circuitería de coordinación. Funciona bien cuando las interacciones entre dominios están protegidas por sincronizadores o lógica de handshake.
--

=== Sequenced Coordination of Reset Removal (Part I)

[.text-justify]
Some **multi-clock designs** require that resets be removed  
in a **defined and prioritized sequence** across clock domains.

==== When to Use
- One clock domain must **start up before another**.  
  → Example: `aclk` logic must be active before `bclk`,  
  and `bclk` before `cclk`.
- Typical in **dependent control/data hierarchies**  
  or when **inter-domain dependencies** exist.

[.notes]
--
Algunos diseños multi-reloj requieren que los resets se eliminen en una secuencia definida y priorizada entre dominios de reloj.
Cuando un dominio debe arrancar antes que otro, como en jerarquías de control/datos dependientes o cuando existen dependencias entre dominios.
--

=== Sequenced Coordination of Reset Removal (Part II)

==== Design Technique
- Use **prioritized asynchronous reset synchronizers**:
  - The **highest-priority synchronizer** input is tied **high**.  
  - Each subsequent synchronizer input is driven by the  
    **master reset output** of the higher-priority domain.

[.notes]
--
Usad sincronizadores de reset asíncronos priorizados: la entrada del sincronizador de mayor prioridad se ata a alto. Cada sincronizador subsiguiente es impulsado por la salida de reset maestro del dominio de mayor prioridad.
--

== Conclusions

[.text-justify]
Properly designed, both **synchronous** and **asynchronous** resets  
can ensure **reliable circuit initialization**.

Key Takeaways
- **Asynchronous resets** are safe for assertion,  
  but their **removal must be synchronized** to avoid metastability.  
- Always use a **reset synchronizer** to combine the  
  benefits of asynchronous assertion and synchronous release.  
- **DFT** with asynchronous resets is practical,  
  provided the reset can be controlled during test.  
- **Distributed flip-flop trees** simplify buffering, timing,  
  and layout issues for both reset styles.
